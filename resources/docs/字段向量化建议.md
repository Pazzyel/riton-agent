# 向量化表格数据

在设计向量化方案时，最核心的原则是：**“只把具有语义推理价值的内容喂给 Embedding 模型，把结构化约束留给元数据。”**

向量化（Embedding）本质上是把文本转为**模糊的语义空间**，而数值（如价格、销量）在向量空间里表现极差。

---

## 商铺

### 1. 字段分类建议表

`shop` 表字段，建议的分类方案如下：

| 字段名 | 向量化内容 (Document) | 元数据 (Metadata) | 不进入向量库 | 理由 |
| :--- | :---: | :---: | :---: | :--- |
| **id** | | **✓** | | 必须保留，用于“回表”查询。 |
| **name** | **✓** | **✓** | | 店名含语义（如“老四川”代表川菜）。 |
| **type_name** | **✓** | **✓** | | 分类是核心语义（如“火锅”、“美发”）。 |
| **area / address**| **✓** | **✓** | | 包含地标语义（如“外滩附近”、“恒隆广场”）。 |
| **x / y / h3hex** | | **✓** | | **硬约束**。向量无法计算精确距离，需用于 Filter。 |
| **avg_price** | | **✓** | | **数值属性**。用于价格区间过滤或排序。 |
| **sold / score** | | **✓** | | **热度属性**。用于后期加权排序（Boosting）。 |
| **open_hours** | | | **✓** | 实时性太强，应在回表后的业务层判断。 |
| **images** | | | **✓** | 向量库存 URL 浪费内存，回表取即可。 |
| **create/update** | | | **✓** | 仅在后台管理或回表更新逻辑中使用。 |

---

### 2. 什么是“适合向量化的内容”？

应该构建一个**“语义描述字段（Text for Embedding）”**，将具有关联意义的字段拼接成一段自然语言。

**推荐做法：** 创建一个虚拟字段 `enrich_text`，内容如下：
> “{name}是一家位于{area}商圈，地址在{address}的{type_name}店。”

**为什么这么做？**
Embedding 模型在处理自然语言句子时效果最好。例如，用户搜索“静安区的川菜馆”，模型能通过 `enrich_text` 里的“静安区”（来自 area）和“川菜”（来自 type_name）实现精准的语义对齐。



---

### 3. 元数据（Metadata）的职责：过滤与加权

向量检索出来的结果往往是“似是而非”的，元数据的作用是进行**“二次剪裁”**：

* **Pre-filtering (预过滤)：** 利用 `h3hex` 限制在 30km 内，利用 `type_name` 锁定行业。
* **Post-Ranking (后排序/加权)：** * 虽然向量分值高，但如果 `score`（评分）很低，或者 `sold`（销量）为 0，你应该降低它的排名。
    * 公式参考：$FinalScore = SemanticScore \times \text{log}(sold + 1)$。

---

### 4. 架构实战建议

在 Elasticsearch 中，你的索引结构（Mapping）应该是：

```json
{
  "properties": {
    "shop_vector": { "type": "dense_vector", "dims": 1536 }, // enrich_text 的向量
    "id": { "type": "keyword" },
    "h3hex": { "type": "keyword" },                          // 用于快速地理过滤
    "type_name": { "type": "keyword" },                      // 用于精确分类过滤
    "avg_price": { "type": "integer" },                      // 用于价格筛选
    "score": { "type": "half_float" }                        // 用于衰减函数加分
  }
}
```

### 总结
* **向量化：** 负责“看起来像什么”（语义）。
* **元数据：** 负责“在哪里”、“多少钱”、“好不好”（硬指标）。

## 团购券

对于团购券（Coupons）的向量化方案，核心逻辑与商铺略有不同：**商铺侧重于“品牌与位置”，而团购券侧重于“消费场景与性价比”。**

在本地生活平台中，用户搜索“划算的二人火锅”或“深夜食堂代金券”时，语义匹配主要发生在 `title` 和 `description` 上。

---

### 1. 团购券字段分类方案

| 字段名 | 向量化内容 (Document) | 元数据 (Metadata) | 不进入向量库 | 分类理由 |
| :--- | :---: | :---: | :---: | :--- |
| **id / shop_id** | | **✓** | | **核心索引**。用于回表查询商铺详情。 |
| **x / y / h3hex** | | **✓** | | **LBS 约束**。确保用户只搜到附近的券。 |
| **shop_name** | **✓** | **✓** | | **增强语义**。用户搜店名时能直接匹配到相关团购券。 |
| **title** | **✓** | **✓** | | **强语义**。如“双人超值套餐”、“晚市代金券”。 |
| **description** | **✓** | **✓** | | **补充语义**。包含菜品、服务细节。 |
| **rules** | | **✓** | | **业务约束**。如“仅限周末”，AI 需读取以回复用户。 |
| **pay_value** | | **✓** | | **价格过滤**。用于“50元以下”等筛选。 |
| **actual_value** | | **✓** | | **计算折扣**。用于计算“性价比”权重。 |
| **type / status** | | **✓** | | **硬性过滤**。只检索 status=1（可用）的券。 |
| **daily_limit** | | | **✓** | **高频变动**。下单前在业务层校验即可。 |
| **create / update** | | | **✓** | 仅用于后台审计。 |

---

### 2. 构建团购券的“语义载体” (Enrich Text)

建议将团购券的语义字段拼接成一个段落进行 Embedding：

> **推荐拼接模板：**
> “商铺“{shop_name}”有团购券可以购买：名称{title}。描述：{description}。适用规则：{rules}。”

**为什么要带上 rules？**
有些 rules 包含重要的语义信息，比如“仅限午市使用”或“无需预约”。当用户搜索“现在就能用的午餐”时，Embedding 模型能捕捉到这种时间相关的关联性。



---

### 3. 高级检索策略：双路加权 (Boosting)

在处理团购券检索时，不能只看向量得分，要引入**“性价比分”**。

$$FinalScore = VectorSimilarity \times \text{Weight}_{discount}$$

* **折扣率系数：** $\text{DiscountRate} = \frac{pay\_value}{actual\_value}$。
* **逻辑：** 在语义相近的情况下，折扣力度更大（$pay\_value$ 远小于 $actual\_value$）的券应该排在前面。

---

### 4. 向量库 Mapping 设计 (Elasticsearch 示例)

```json
{
  "properties": {
    "coupon_vector": { "type": "dense_vector", "dims": 1536 },
    "shop_id": { "type": "keyword" },
    "h3hex": { "type": "keyword" },
    "pay_value": { "type": "integer" },
    "type": { "type": "integer" },
    "status": { "type": "integer" }
  }
}
```

---

### 5. 跨表检索的架构考量

用户通常是**“先搜店，再看券”**或者**“搜券，顺便看店”**。

* **方案 A (冗余存储)：** 将商铺的 `type_name`（如：火锅）也存入团购券的 Metadata 中。这样用户搜“火锅券”时，可以直接从团购券索引里一把抓。
* **方案 B (多路召回)：** 就像我们之前讨论的，分别检索“商铺索引”和“团购券索引”，然后通过 `shop_id` 在内存或 ES Retriever 中做 Join。

**建议：** 为了极致的查询性能，**方案 A（适度冗余）** 更适合高并发的移动端搜索场景。

## 评论

在本地生活平台中，**用户评论/贴文（Blogs）** 是 RAG 系统中最重要的“感性数据源”。与商铺和团购券不同，评论的数据特征是**非结构化程度极高**、**情感色彩浓厚**且具有**时效性**。

以下是针对 `BlogVectorizeDto` 的向量化与元数据分类建议：

---

### 1. 用户评论字段分类方案

| 字段名 | 向量化内容 (Document) | 元数据 (Metadata) | 不进入向量库 | 分类理由 |
| :--- | :---: | :---: | :---: | :--- |
| **id / shop_id** | | **✓** | | **关联核心**。用于定位具体商家。 |
| **shop_name** | **✓** | **✓** | | **增强语义**。用户搜店名时能直接匹配到相关评论。 |
| **x / y / h3hex** | | **✓** | | **LBS 约束**。过滤“附近的人”发的贴文。 |
| **title** | **✓** | **✓** | | **主题语义**。通常是用户对体验的高度概括。 |
| **content** | **核心 ✓** | | | **主要语义源**。包含细节描述、口味、服务等。 |
| **liked / comments** | | **✓** | | **热度权重**。用于高质量内容优先展示。 |
| **images** | | | **✓** | 图片链接不含文本语义，回表获取。 |
| **create / update** | | **✓** | | **时效性过滤**。用户通常更关心近期的真实体验。 |

---

### 2. 构建评论的“语义指纹” (Enrich Text)

评论的向量化不能简单地只存 `content`，因为用户发帖时可能不会重复提店名或位置。为了让检索更精准，建议采用**“内容 + 环境”**的拼接方式：

> **推荐拼接模板：**
> “关于店铺“{shop_name}”的评价：标题：《{title}》。内容：{content}”

**为什么要加入 `shop_name`？**
如果用户只写了“这家的毛肚非常脆”，向量库里只有这句话。当其他用户搜“海底捞 毛肚”时，由于原始评论没提“海底捞”，匹配度会下降。加上店名能显著提升**“店名 + 体验”**复合搜索的召回率。

---

### 3. 针对评论的特殊 RAG 策略

作为后端，在处理评论向量时，建议引入以下两个逻辑：

#### A. 长度过滤与清洗
评论质量参差不齐。在进入向量化 Pipeline 之前：
* **剔除超短文本：** 如“好评”、“111”等无意义内容，不占用向量库空间。
* **长文本分段（Chunking）：** 如果 `content` 超过 500 字，建议按段落切分，每段独立 Embedding，但指向同一个 `id`。

#### B. 社交热度加权 (Social Boosting)
利用 `liked`（点赞）和 `comments`（评论数）进行排序干预。

$$Score_{final} = VectorSimilarity \times (1 + \alpha \cdot \log(liked + 1))$$

**业务逻辑：** 语义相似的前提下，高赞的高质量“种草文”应该排在前面，因为它们对用户的决策影响力更大。

---

### 4. 向量库 Mapping 设计 (Elasticsearch 示例)

```json
{
  "properties": {
    "blog_vector": { "type": "dense_vector", "dims": 1536 },
    "shop_id": { "type": "keyword" },
    "h3hex": { "type": "keyword" },
    "liked": { "type": "integer" },
    "create_time": { "type": "date" }
  }
}
```



---

### 5. 多模态的未来

由于 `images` 存在，未来可以升级为**多模态检索 (CLIP)**。
* 将 `images` 中的图片也进行向量化。
* 当用户搜“环境优雅的火锅店”时，系统不仅能匹配文字，还能通过图片特征（装修风格）找到对应的评论。
