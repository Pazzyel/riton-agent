# 多路召回与融合排序（Multi-Route Retrieval & Fusion Ranking）问题

如果一个商铺在“基础信息”、“热销商品”和“真实评价”三个维度都与用户需求匹配，那它确实应该排在更前面

要实现这个逻辑，后端通常采用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 算法。这是一种无需对不同向量库得分进行归一化（Normalize）就能直接融合权重的经典方案。

---

## 1. 核心流程：多路并行检索与融合

### 步骤分解：
1.  **并发检索：** Agent 将用户意图拆解为三个查询向量，并行请求三个库。
    *   **库 A (商铺)：** 匹配环境、位置、分类。
    *   **库 B (商品)：** 匹配具体菜品、团购套餐。
    *   **库 C (评论)：** 匹配口感、服务、氛围等感性体验。
2.  **ID 对齐：** 每个库返回各自的 Top N（如 Top 20）商铺 ID 及其原始得分。
3.  **RRF 评分计算：** 对每个 ID 在三路结果中的排名进行加权求和。

### RRF 公式逻辑：
对于每一个商铺 $m$，其最终得分 $Score(m)$ 计算如下：
$$Score(m) = \sum_{q \in \{Shop, Item, Review\}} \frac{1}{k + rank_q(m)}$$
*   $rank_q(m)$ 是商铺 $m$ 在查询路 $q$ 中的排名（从 1 开始）。
*   $k$ 是一个常数（通常取 60），用来平滑排名非常靠前的样本。

**直观理解：** 如果一个店在三路都在前 5 名，它的分值会远高于只在某一路拿第一、其他路没进前 100 的店。

---

## 2. 后端架构实现方案

在 LangGraph 或后端服务中，可以设计一个 **“聚合器（Aggregator）”** 逻辑：

### 实现代码示例 (Python 伪代码)
```python
def reciprocal_rank_fusion(results_list, k=60):
    """
    results_list: List of Lists, 每个 List 包含该路召回的 merchant_id
    """
    fused_scores = {}
    for results in results_list:
        for rank, m_id in enumerate(results, start=1):
            if m_id not in fused_scores:
                fused_scores[m_id] = 0
            # 排名越靠前，增加的分值越大
            fused_scores[m_id] += 1 / (k + rank)
            
    # 按得分从高到低排序
    return sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
```

---

## 3. 进阶：带权重的融合 (Weighted Hybrid)

不同向量库的重要性可能不同。例如：用户搜“想吃红烧肉”，商品库的权重应该高于评论库。

你可以引入 **权重因子 $w$**：
$$Score(m) = w_1 \cdot RRF_{shop} + w_2 \cdot RRF_{item} + w_3 \cdot RRF_{review}$$

*   **商品库权重：** 当用户提到具体食物名称时，调高商品路权重。
*   **评论库权重：** 当用户提到“浪漫”、“带娃”、“安静”等形容词时，调高评论路权重。

---

## 4. 这种方案的优势

1.  **解决量纲不一问题：** 商铺库的余弦相似度可能是 0.95，而评论库因为文本杂乱可能最高才 0.7。直接比分值不公平，但**比排名**永远是公平的。
2.  **提升稳定性：** 避免了单一向量库因为噪声（比如某条奇怪的评论）导致的推荐偏差。
3.  **后端扩展性：** 未来如果你增加了一个“达人笔记向量库”，只需要在并发检索中多加一路，最后扔进 RRF 函数即可。

---

### 💡 后端落地建议：
建议在 **Elasticsearch** (支持内置 RRF) 或 **Milvus** 中直接利用其多向量检索能力。如果手动实现，记得在多路检索时使用 `asyncio.gather` 并行查询，否则三路串行会导致 API 响应时间（RT）翻倍。

**根据用户的 Prompt 动态调整这三路召回的权重（Weights）**
